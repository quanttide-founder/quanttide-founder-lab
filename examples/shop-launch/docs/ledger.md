# 算账工具使用说明

`src/ledger.py` 的用户文档。回答三件事：它算什么、怎么调、结果怎么读。

工具只做框架中 A 类（抽象推理）环节的测算 —— 财务与结构推导。它不预测口味、人流、现场，也不替你判断该不该开店。

## 准备

需要 Python 3.10+，无第三方依赖。在 `shop-launch/` 目录下运行：

```sh
python3 src/ledger.py --help
```

改了代码先跑自检，确认数学关系没被改坏：

```sh
python3 src/ledger.py selftest    # 12 项全过才继续
```

## 参数的三级来源

工具的每个数字都标了来源，**读输出时先看标注再看数值**：

| 标注 | 含义 | 可信度 | 能否覆盖 |
|------|------|--------|----------|
| `[锁]` | 取自 `data/火锅串串.md`，已由实地探店校准 | 高 | 不得覆盖 |
| `[L0]` | 未验证假设，由命令行显式给出 | 低 | 探店后必须更新 |
| `[L1]` | 待回填，尚未取得 | 无 | 取得数据后填入 |

**这是工具最重要的约定**：L1 缺失时它拒绝计算该段并打印缺口（退出码 `2`），而不是给一个看起来合理的数字。AI 财务测算的分数取决于输入质量 —— 输入缺失时，「算不出来」比「算出一个数」更有价值。

## 命令一览

| 命令 | 算什么 | 需要的输入 |
|------|--------|-----------|
| `per-head` | 人均拆解：扣掉锅底后能吃多少签 | `--mix`（可选） |
| `pot` | 底料摊薄到每签的成本 | 无 |
| `stall` | 摆摊阶段达标判定与营收测算 | `--daily`（可选，L1） |
| `shop` | 档口店净利率与盈亏平衡点 | 4 项 L1 参数 |
| `gaps` | 列出全部待回填项 | 无 |
| `all` | 以上全部 | 混合 |
| `selftest` | 自检 | 无 |

`--mix 素:荤:招牌` 是签型比例，默认 `60:30:10`。**这个默认值是 L0 占位假设**，所有营收测算都挂在它上面；探店带回荤签品类后，第一件事就是改它重算。

## 典型用法

### 第一次跑，看清还缺什么

```sh
python3 src/ledger.py all
```

不带参数跑，工具会用 `[锁]` 和 `[L0]` 算出能算的部分，把算不出来的列成缺口。此时退出码是 `2`，表示有待回填项 —— 这是预期结果，不是错误。

### 摆摊期回填实测

```sh
python3 src/ledger.py stall --daily 149
```

```
  达标线        [锁] 连续 4 周日均 150 签
  实测日均      149 签 → 差 1 签/天
```

达标线是 `≥ 150`，差 1 签也不算达标。连续 4 周是累计条件，`--daily` 传入的应是这 4 周的日均值，不是单日峰值。

### 档口店测算

```sh
python3 src/ledger.py shop \
  --staff 8000 --utility 2000 --other-fixed 1000 --food-rate 0.35
```

```
  固定成本      3,500(租) + 8,000(人工) + 2,000(水电) + 1,000(其他) = 14,500 元
  变动成本率    46.4%（食材 35.0%×(1+损耗 10.0%) + 底料 7.9%）
  预估净利      9,628 元 → 净利率 21.4%  ✔ 达标
  盈亏平衡点    27,043 元/月（达成营业额的 60%）
```

四个 L1 参数缺一个都不算（退出码 `2`）。人工、水电、食材成本率需要询价或当地用工调研取得。

## 结果怎么读

### 人均拆解

```
  签子可花      [锁] 35–50 元
  人均签数      推算 28–62 签
```

人均目标和锅底价定下后，签子预算就是死数。反推出的 28–62 签是**对运营的约束**：人均要吃到这个量，串签效率、上菜速度、翻台率都得跟上。这个数若明显做不到，说明人均 55–65 元的定价站不住。

### 底料摊薄

```
  每签底料      推算 0.060–0.100 元
```

底料摊到每签不到 1 毛钱，占人均成本比例极小。谈底料供应时，这个数意味着**不必为省几块钱牺牲品质** —— 差价换算到每签上几乎无感，而味道是复购的关键。

### 摆摊营收

```
  28 天累计     推算 3,360–5,166 元
  投入          [锁] 15,000–30,000 元
```

两者差 6–10 倍。注意口径不同：投入是设备、押金等一次性成本，营收是流水。**结论是摆摊期靠营收回本无望** —— 这阶段的产出不是利润，是配方验证、客流数据和 300 个微信。如果把摆摊当赚钱环节来评估，会得出错误判断。

### 盈亏平衡点

```
  盈亏平衡点    27,043 元/月（达成营业额的 60%）
```

即月营业额做到 45,000 的 60% 就不亏。**60% 这个比例比绝对值更有用** —— 它是安全边际。比例越低越抗跌，越高则营业额一波动就转亏。与净利率一起看：净利率达标但平衡点贴近营业额，说明固定成本过重，抗风险差。

## 图形界面（GUI）

```sh
python3 src/ledger_gui.py
```

三层报表结构，与 CLI 输出同源（共用 `present()` 与公式函数）：

| 层 | 内容 | 特点 |
|----|------|------|
| 第一层 | 月利润、保本线、安全倍数 | 大字，一眼定生死 |
| 第二层 | 收入侧与成本侧逐项拆解 | 中字，可核查，每行带来源标签 |
| 第三层 | 签型比例、翻台/客流、固定成本、行业参考 | 折叠，想抠再看 |

顶栏切换 **摆摊 / 档口店** 两种模式，右侧数据完整度条随输入实时变化。空字段即 L1 未回填。

### 与 CLI 的策略分歧

**刻意设计，不是不一致**：

| | 参数缺失时 | 理由 |
|---|---|---|
| CLI | 拒绝计算，退出码 `2` | 脚本靠退出码判断，静默默认值危险 |
| GUI | 用估算值代填，一层加 `[试算]` 徽标，完整度同步下降 | 面对人，空白窗口不如标注清楚的估算 |

两边共用 `present()`、公式函数与 `GAPS` 常量，不复制算术。

### 数据完整度

```
数据完整度 ▓▓▓▓░ 80%
```

分母是**该模式**下的 L1 参数个数：

- 档口店 5 项 —— 客单价、日客流、人工、水电其他、食材成本率
- 摆摊 2 项 —— 实测日均、实际损耗率

**估算项不计入已填**。这是第一层结论的可信度指标：100% 表示全部实测回填，低于此按比例打折看待。

| 状态 | 徽标 | 颜色 |
|------|------|------|
| 100% 且无估算 | 无 | — |
| 含估算值 | `[试算] 含 N 项估算值，完整度 X%` | 橙 |
| < 100% | `完整度 X%，部分实测未回填` | 橙 |
| 关键 L1 缺失 | `⚠ 部分 L1 未回填，结论待补全`（一层显示「无法计算」） | 红 |

### GUI 自检

窗口底部常显 `自检 PASS / FAIL`，启动时跑一次 `selftest()`。改了计算代码后开窗口确认它仍是 PASS。

## 边界

- **不算 C 类**（现场、感官、随机性）。翻台率、口味、客流这些它碰不到 —— `gaps` 里列出它们正是因为无法计算
- **数字不等于已验证**。工具输出是结构化推导，A 类论证再充分也不改变 B/C 类的证据等级
- **`[锁]` 值有单一来源**。若 `data/火锅串串.md` 的锁定项变动，需同步改 `src/ledger.py` 中的 `LOCK` 字典（该对应关系在代码注释中标出）
