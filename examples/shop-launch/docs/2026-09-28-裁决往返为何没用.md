# 裁决往返为何没用 — 设计偏差反思

2026-09-28。裁决机制连改三版：Label Studio 评审卡往返 → 8 条直答队列 → 判例/成文法双库。前两版被连续判否，本篇记偏差本身；过程细节看 git 历史。

## 偏差

1. **复制了形式，没复制问题域**。task-board 的四枚标签（先做/缓做/不做/有异议）答的是「排不排期」，这里要答的是「分数采不采纳、谁兜底」——答非所问。把「接入 task-board」读成了「复制它的配置」。
2. **写回映射为验收而造**。「先做+理由 → L0→L1」「有异议 → 已证伪」，标签与证据等级之间没有语义联系，是硬凑的 if 语句：流水的输出（标注）冒充了框架的输入（证据）。
3. **对象混装**。15 条队列里 7 条是 L1 缺口——要数据不要投票，翻台率不会因为打了「缓做」就变成 L1。
4. **单人 8 问，搭了多人评审设施**。幂等 history、配置复制、按 title 对账都是多评审人多轮的设计；摩擦大于收益的流程必被跳过——「建项目被漏掉」是设计在报警，当时却当执行失误修补，是同一偏差的延续。
5. **先搭流水，后验问题**。真实需求是「AI 判、人抽查」，流水却是「人逐条答」；该先人肉走通一轮再决定要不要界面。
6. **换作答方式不解决形态问题**（第二版教训）。改成「8 条直答 + 采纳/否决/存疑」仍是把决策摆在人面前逐条拍板，证据等级还跟着人的表态走——队列这个形态本身就是把决策负担转移给人。

## 根因

把跨实验复用当成形式复用（复制配置、标签、流程），而不是问题匹配（裁决单元、裁决人、轮次是否同构）；且把「人的表态」当成了「证据」。task-board 界面的价值来自它的场景前提——任务多、评审人多、意见跨轮累积——这些前提在 shop-launch 一个都不成立。

## 终态

判例与成文法都**显式存**，各配与之匹配的标注：

| 层 | 存储 | 标注 |
|----|------|------|
| 判例（具体决策） | `data/能力对照表.csv` 八字段（依据法条 + 复核） | 复核：维持 / 改判（抽查制，改判终审、重放不覆盖） |
| 成文法（决策准则） | `AGENTS.md` 条文带 § 编号，`assess.py` 为投影 | 修订：改条文 → 同步投影 → 重放，`git diff` 即影响面 |

证据等级与表态脱钩，L1/L2 只认数据到达；C 类走实地动作不出题。机制见 `AGENTS.md`「人机对齐」，用法见 `docs/alignment.md`。实验指标：**放大率 = 一次法条修订覆盖的判例数 / 干预次数**。

## 门槛与遗留

- 再搭界面的门槛：评审人 ≥ 2 或轮次 ≥ 2 或裁决项 ≥ 30，三者均不满足就直答 / 改文件
- Label Studio 项目已删除（2026-09-28，标记质量差、界面出局），标注全部由本地 GUI（`src/review_gui.py`）完成；8090 实例进程保留（环境级资源，属其他实验）
