# 裁决往返为何没用 — 设计偏差反思

日期：2026-09-28。触发：ROADMAP Phase 2 按 task-board 模式搭了 Label Studio 往返，建项目、导入 15 张评审卡，打开即被判没用。此前一轮还把「没有项目」当执行遗漏去补——补完才暴露真正的设计问题。

## 五个偏差

### 一、复制了形式，没复制问题域

task-board 的四枚标签（先做/缓做/不做/有异议）回答的是「这个任务排不排期」；shop-launch 的裁决问题是「这个分数采不采纳、含 C 的部分谁兜底」。卡片上写着「市场调研：L0 分 80 采不采纳」，选项却是「先做」——答非所问。把 ROADMAP 的「接入 task-board」读成了「复制它的配置与标签」，而不是先问：这个实验的裁决单元是什么、裁决人是谁、要答几轮。

### 二、写回映射是为验收而造的缝合

「带理由的先做 → L0→L1」「有异议 → 已证伪」：标签与证据等级之间没有语义联系，是为了满足验收条款（「标注写回、推进证据等级」）硬凑的 if 语句。有异议可能只是分数偏高，不等于结论被证伪；标注是判断，L1 的定义是本地实地数据，两者被一行代码强行等同。**流水的输出（标注）冒充了框架的输入（证据）**——写回的不是证据，是仪式。

### 三、对象混装：要数据的被送去投票

15 条里 7 条是 L1 缺口（翻台率、客单价、食材成本率……）。它们要的是探店、询价、盘点，不是裁决——翻台率不会因为打了「缓做」就变成 L1。根源：队列素材照抄 TODO 的三处来源，没逐条问「这条需要的是裁决还是数据」。真正可裁决的只有 8 条（5 条 L0 假设 + 3 条 C 类判断）。

### 四、单人 8 问，搭了多人评审的设施

往返 6 步（build → export → 开 Web 建项目 → 导入 → 标注 → 导出 → merge），其中幂等 history、配置复制、按 title 对账，全是为多评审人、多轮次、意见累积设计的。这里的裁决人只有 1 个，大概率 1 轮。**摩擦大于收益的流程一定会被跳过——「建项目」被漏掉就是设计在报警**，而上一轮把它当执行失误修补，还用从本地 DB 扒的一次性 token 手搓 API：修补本身也没沉淀进工具，是同一个偏差的延续。

### 五、先搭流水，后验问题

快更迭原则写得很清楚：代码按需快速搭建，只服务当前一轮验证。真实需求是「8 个问题等人答」，流水却是「Label Studio 往返」。正确顺序：先人肉走通一轮（列问题 → 口头作答 → 改表 → check），确认卡点真的在「作答界面」，再决定要不要界面。实际把顺序做反了，于是流水建完才发现问题本身不需要流水。

## 根因

把跨实验复用理解成了**形式复用**（复制 config、标签、流程），而不是**问题匹配**（裁决单元、裁决人、轮次是否同构）。task-board 界面的价值来自它的场景前提：任务多、评审人多、意见要跨轮累积——这些前提在 shop-launch 一个都不成立。

## 纠正（本次执行）

1. **队列只留可裁决项**：8 条（L0 假设 5 + C 类判断 3）；L1 缺口移出，回 `ledger gaps` 与 3.3 数据回填
2. **答案词汇换成本领域**：`采纳 / 否决 / 存疑` + 理由，替换排期标签
3. **写回改状态式**：采纳+理由 → L0→L1；否决+理由 → 已证伪；存疑 → 不动；L2 行拒绝覆盖。状态式天然幂等，不再需要 history 机制
4. **删 Label Studio 中间层**：清单导出、配置副本、标注解析全部移除（失效即删，见 git 历史）。作答直接写 `data/裁决队列.json` 的 `feedback`（对话代填或手改），`review_merge.py` 只做校验与写回
5. **分数调整不走标签**：直接改 `data/能力对照表.csv`，`assess check` 把关

## 下次搭界面的门槛

评审人 ≥ 2，或轮次 ≥ 2，或裁决项 ≥ 30——三者均不满足时，直接改文件 / 对话作答，不建界面。

## 追记一（同日第二轮）：直答仍是把决策负担转移给人

把 15 卡裁决队列改成「8 条直答 + 采纳/否决/存疑」后仍被判不对。根子在：**队列本身预设了「人来逐条做具体决策」**——不管有没有界面，8 个问题摆在人面前就要 8 次拍板，脚本只是记录器，证据等级还跟着人的表态走。对齐方向反了：

- 错的形态：人答决策 → AI 存档 → 表态推进证据
- 对的形态：AI 按准则自主决策 → 人只投可复用的纠偏 → 准则修好后重放，一次干预覆盖全表

## 追记二（同日第三轮）：判例与成文法都要显式存，各配标注

纠偏仍不够具体——补上存储与标注的对应关系：

| 层 | 显式存储 | 人的标注 | 成本 |
|----|---------|---------|------|
| 判例（具体决策） | `data/能力对照表.csv` 八字段（+ 依据法条 + 复核） | 复核：维持 / 改判（改判终审，重放不覆盖） | 便宜，抽查制 |
| 成文法（决策准则） | `AGENTS.md` 条文（`标尺`、`检查§1–4`、`硬约束§n`） | 修订：改条文 → 同步 `assess.py` → 重放 | 贵，归纳制 |

两个库靠 `依据法条` 列互链：判例引用条文，条文修订时反查受影响判例，`git diff` 行数即放大率。证据等级与表态彻底脱钩，L1/L2 只认数据到达。实验指标从「人答完多少条」改为**放大率 = 一次法条修订覆盖的判例数 / 干预次数**。
