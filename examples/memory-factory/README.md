# memory-factory

反向蒸馏：把已定型的档案当索引，回扫旧日志，把「档案没覆盖但日志里存在」的碎片捞出来、归位、补回档案。

## 与既有链路的关系

记忆仓库（`assets/memory`）已有的四道蒸馏是**正向**的——日志产出档案、路线图、洞察、意图（`.agents/skills/journal-to-*`）。本案例是它的**反向**操作：用档案去丈量日志，做差集。

前提因此自然成立：档案本来就是日志的有损投影，差集必然非空。

## 交付方式

与操作者的约定。前四条管本案例交出什么，后两条管人机之间怎么走。

**一、交给操作者的东西只有四类**

| 交付物 | 位置 | 形态 |
|:--|:--|:--|
| 规格 | `docs/` | 可执行的规则——做什么、判据、步骤、验收 |
| 假设 | `docs/assumption.md` | 程序立在什么假设上，哪一层不成立 |
| 数据 | `data/` | JSON，程序之间流转 |
| 报告 | `data/report/<日期>-<描述>.md` | 人读的碎片报告与验收结果 |

**二、程序不碰档案。** 只读日志与档案，产出报告；档案的每次改动由操作者确认后写入。程序不自动改档案，也不写 `docs/`。

**三、人读的一律纯文本。** 报告、标注任务、验收结果一律 Markdown 或 JSONL，能在编辑器里直接看与改——不塞二进制，不塞数据库，是压缩件就解开。

**四、分工线。** 机器判机械正确性（分块、匹配、聚类、判型），操作者判意义（认不认、值不值、矛盾保留了没有）。机器不替操作者裁决意义。

**五、协作节奏。** 判据定完就静默做完，只在出结果时报一行；过程细节留在文件里，不进对话。低风险的执行决定自行处理；动到判据、结构或档案，先问。

**六、一次完备。** 交付在第一次就完整——含入口、含怎么跑、含怎么核。
